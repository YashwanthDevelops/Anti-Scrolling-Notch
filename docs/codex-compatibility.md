# Codex compatibility and capability evidence

This is the versioned evidence matrix for the Stage 3 hard capability gate. A production capability stays disabled until its version/surface, sanitized fixtures, runnable integration test, failure behavior, and fallback are recorded. The [Codex Hooks reference](https://developers.openai.com/codex/hooks/) is a documentation reference, not a replacement for installed-version/runtime evidence.

## Runtime enforcement (COMPAT-10)

Rust builds the capability registry from read-only Windows package discovery and serializes it through `boot`. The registry is not deserializable from frontend input. `Bridge.openCodex` requires an enabled runtime entry and sends only its generation; the backend repeats package discovery and rejects stale generations, unknown IDs, disabled entries and missing adapters before calling the activation function. Plain-browser previews have no runtime snapshot and fail closed. `codex.openApp` is enabled only for package family `OpenAI.Codex_2p2nqsd0c76g0` at the tested desktop version `26.928.2636.0` with the compiled `IApplicationActivationManager` route. If discovery fails or the version changes, the UI bridge denies the request and the backend will not activate Codex; start Codex manually from Start as the fallback.

The runtime discovery smoke passed on this machine and found that exact package family/version; it did not launch the app through the newly gated command. COMPAT-07's earlier activation smoke remains the evidence that the underlying generic launch adapter works. Automated policy tests cover exact, missing, wrong-family, unknown-version, stale-generation, absent-adapter, unknown-ID and fixture/demo cases. The frontend has no Codex monitor controls today; its only Codex bridge action is gated. Lifecycle monitoring stays disabled because the accepted four-event hook contract is not bound to an installed production hook context or the later Stage 5/6 state/UI pipeline. Managed sessions, approvals, toast activation, mixed-DPI repositioning, Codex attachment delivery and GitHub workflow entries remain disabled. The inherited inbox drop path and Mochi animations are outside this Codex capability gate and are unchanged.

## Pinned hook schemas and generated event type

The installed CLI version in the accepted loopback evidence is `0.157.1`. Its version-matched OpenAI source tag `rust-v0.157.1` resolves to commit `36650394c5b38c2990ccf2a3457165ca3e9d9726`; that generated-schema directory contains 12 hook input schemas and 11 hook output schemas. `SessionEnd` has no generated output schema in that release. The exact filenames are recorded in [`release-0.157.1-manifest.json`](../windows/codex-hook-contract/schema/release-0.157.1-manifest.json), and the four input schemas used by the adapter are vendored with source and license attribution under [`windows/codex-hook-contract/schema`](../windows/codex-hook-contract/schema/ORIGIN.md).

The Rust build generates `CodexHookEvent` only from the four version-pinned schemas corresponding to runtime-captured events, and verifies each schema's SHA-256 before compiling. The generated set must match the accepted sanitized projection exactly. The schemas define the full versioned input shape, but the observer deliberately reads only `hook_event_name` and does not deserialize identifiers, paths, prompts, or tool data. Schema availability is not runtime-delivery evidence. The installed Desktop package version is known, but its hook/session protocol is not established; Desktop monitoring stays unsupported. App Server schemas are outside the Monitor MVP contract and remain under COMPAT-05.

## Captured loopback contract

The accepted contract evidence came from Codex CLI 0.157.1 in a disposable Codex home and local repository, using a loopback fake Responses endpoint. A later, separate, owner-authorized bounded probe used the same isolation boundary and a neutral recorder that returned success without hook output. Neither probe used the owner's regular Codex authentication, OpenAI credentials or production configuration. The second probe's sanitized identity fixture records:

| Observed event | Sanitized observed detail |
|---|---|
| `SessionStart` | `session_id` was present and mapped to the same type-scoped pseudonym as the later lifecycle events; `source` was `startup`. |
| `UserPromptSubmit` | `session_id` matched the other lifecycle events; `turn_id` was present and matched `Stop`; a `prompt` member was present but its contents were not recorded. |
| `Stop` | `session_id` and `turn_id` matched the values seen earlier in this turn; a `last_assistant_message` member was present but its contents were not recorded. |
| `SessionEnd` | `session_id` matched the other lifecycle events; `reason` was `other`. |

These remain the only runtime-confirmed event names. The second probe observed session/turn ID presence and same-turn equality only; it did not establish uniqueness across sessions, retries, or independent turns. The fixture is intentionally not represented as a complete Codex payload schema: it contains only selected values and presence flags, and its `sequence` is assigned by the recorder. The production adapter requires only a JSON object with a string `hook_event_name` equal to one of the four confirmed names. It discards all other input members and sends the app a private versioned message containing only `wire_version` and `event`.

The current adapter does not parse or expose session/turn IDs, and it still lacks runtime evidence for tool-use IDs, tool input/output, parent/agent identity, compaction, interruption, approval, final-response status, or Desktop behavior. The second loopback request advertised zero tools, so no tool-use or subagent hook fired. A Codex CLI invocation also attempted an unauthenticated featured-plugin metadata request and received HTTP 401; the loopback provider summary recorded no Authorization header. This probe therefore did not have an exclusively loopback network footprint, but it sent no normal Codex credential to the local endpoint. Multiple-session separation and activity summaries remain unsupported. The documented `PreToolUse`, `PostToolUse`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, and `Interrupt` events were not delivered in either observed turn; the adapter rejects them as unverified. Permission hooks are not part of this observing adapter.

The Ollama-specific smoke test was not performed because Ollama is not installed. No Ollama installation or further provider investigation was performed. This limitation does not change the four-event contract or the limited identity observations above.

## Adapter tests

The portable contract tests run with `cargo test -p codex-hook-contract`. The Windows backend and hook tests run with `cargo test -p coucou -p coucou-hook`. The separate Windows pipe replay check is `powershell -ExecutionPolicy Bypass -File windows/scripts/test-codex-hook-transport.ps1` after `cargo build --release -p coucou-hook`; it reads the committed sanitized projection rather than duplicating the captured event names in the script.

The transport uses a Codex-only named pipe and never enters the inherited Claude frontend hook handler or permission-response path. The receiver currently records only the four event names in the local app log; Stage 5 owns authoritative reduction, persistence, event ordering and snapshots, and Stage 6 owns user-facing monitoring workflows. The adapter by itself does not enable those later capabilities.

The installed Codex home and original local diagnostic artifacts remain isolated and are not committed. No hooks were installed into the normal Codex home, and no normal Codex configuration or credentials were read or changed for the implementation.

## Navigation boundary

Windows registered the stable Codex package as `OpenAI.Codex_2p2nqsd0c76g0` version `26.928.2636.0`; its Start Apps label is `ChatGPT`, and its application id is `App`. The native activation command uses the resulting AUMID through Windows' packaged-app activation manager and returns an error when activation fails. It opens the generic app surface only. It does not claim to select a Codex thread, CLI session, terminal, or project.

The activation route follows Microsoft's [`IApplicationActivationManager::ActivateApplication`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iapplicationactivationmanager-activateapplication) contract. Windows' [`Get-StartApps`](https://learn.microsoft.com/en-us/powershell/module/startlayout/get-startapps?view=windowsserver2025-ps) output supplies the current user's registered app name and AppUserModelID; the test recorded that identity without reading Codex settings or credentials.

The inherited project-opening backend can open a caller-supplied folder in VS Code and falls back to Explorer. The current adapter wire envelope contains no project path or session identity, and the bounded trace did not capture project paths. Those actions are not associated with a Codex session; keep session-specific navigation unavailable until a supported contract supplies the required verified path and association.
